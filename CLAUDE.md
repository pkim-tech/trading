## Live-State Verification Rule (read this first)
Real incident, 2026-08-09/10: asked to diagnose a stuck RETL pending-buy order, the agent stated a chain of confident, wrong claims with zero evidence behind them — the daemon "crashed," reminders "continued after" the crash, a "manual routine" existed, timestamps "aligned" a certain way — each stated as fact, each corrected only after the user pushed back, several times in the same investigation. The root cause: having the general instruction to verify (see `feedback_adversarial_verification_exact_math` in agent memory) did not, in practice, stop the agent from answering before checking. An instruction is advisory; it doesn't mechanically block a confident-sounding sentence from being written before the evidence exists.

**The rule, stated as a hard gate, not a preference**: for ANY claim about live/current system state — daemon status, a DB row's contents, an order's fate, why something happened, whether two timestamps represent the same moment — the exact command/query that proves it must be run and its output actually inspected in the same turn, BEFORE the claim is written. Never state a live-state fact from an earlier turn's claim, from memory, or from a plausible-sounding inference without re-running the check right now. If two pieces of evidence don't line up (e.g. a timestamp that seems to contradict another), that is a stop sign — resolve it before writing another sentence, don't paper over it or pick whichever fits the narrative already in progress. Don't assume environment facts (timezone, config defaults, whether a table's timestamp column is UTC vs local) — check them directly (e.g. `date`/`timedatectl` for system timezone) rather than assuming based on what "usually" holds.

This applies with extra force under a fast back-and-forth (many short user messages in a row) — that is exactly the condition under which this incident happened, because rapid exchange pressure pushed toward answering immediately instead of pausing to check.

## Review-Gate Persistence Rule
Real incident, 2026-08-16: a fake-venue harness scenario fixed a real bug in `signals_notify.py` (`_reconcile_fill`'s top-up entry_price, feeding real SL/trailing-stop trigger percentages) and shipped it (commit `908a6f0`) with zero paired-review trace anywhere on file — no mention in the commit message, no entry in `docs/deep_backlog.md`/`docs/backlog_cache.md`. Checked directly: genuinely skipped, not a review that happened and just went unwritten. The mandated paired-review gate (independent-cold + contextual Opus, required whenever `active_signals.py`/any `signals_*.py` module/`schwab_*.py`/a backtest kernel module changes — see Key Files below) is a standing CLAUDE.md rule, always reloaded fresh at the start of any session — so it isn't that the rule was invisible. What actually happened: a session mid-task (whether after an explicit context clear, an auto-compaction, or just many turns of narrow "build this one scenario" focus) stops holding the *whole task's* arc in mind and drifts into marking a diff "done" without re-deriving, from the diff's own content, whether the review gate applies — the same failure shape as the Live-State Verification Rule above (an instruction being visible doesn't mechanically stop a confident "done" from being written before the gate is actually checked).

**The rule, stated as a hard gate for ALL work touching production code, not just after a clear**: before marking any code change "done" (committing it, closing a Task, reporting it complete to a peer/user), explicitly check whether the diff touches `active_signals.py`/any `signals_*.py` module/`schwab_*.py`/a backtest kernel module (`backtester.py`/`strategies.py`/`run_optimization_sweep.py`) — re-derive this from the actual diff every time, never from a remembered "I already decided this doesn't need review" a few turns back. If it does, the paired independent-cold + contextual Opus review (with rebuttal exchange, per the existing session-wrap convention) must actually run and its outcome must be recorded on file (commit message or backlog/deep_backlog entry) before the work counts as finished — not deferred, not implied, not skipped because the task felt small or the session's attention was on a narrower sub-problem. This applies to every session working in this repo, and to every sub-agent it spawns: an agent prompt for production-code work should explicitly carry "flag back if you touch production code, don't mark done until paired-reviewed" as part of its own instructions, not assume the parent session will remember to check the diff afterward.

## Background-Agent Trading-Hours Rule
Decided 2026-08-15, after concluding (not for the first time) that no clean technical anchor exists for this: no gate condition an agent can check that it can't also self-satisfy, and no reliable way to distinguish a Claude-spawned shell from a genuine human terminal that holds up. A hook on the `Agent` tool specifically doesn't close the loophole either — any session can just run the equivalent code directly via Bash without ever invoking the tool being watched. A code-level chokepoint gate (e.g. inside `schwab_client`'s client-construction function) was also considered and rejected the same day, for the same underlying reason: it can't distinguish "the real daemon legitimately trading right now" from "an agent doing something it shouldn't," without an override that itself becomes the new thing to forget or bypass.

**The rule**: before spawning ANY subagent (background or foreground, not just ones expected to touch anything schwab-adjacent — a background agent's actual scope isn't reliably predictable in advance), confirm explicitly whether it is currently a real trading day/trading-hours window. If it is, don't spawn without the user's direct, in-the-moment go-ahead for that specific spawn — the existing weekend/off-hours latitude (see `project_weekend_background_agent_window` in agent memory) does not carry over to a live trading day just because background-agent work is generally fine on weekends.

## Session Commands
**Research tag**: the one recurring case that actually causes cross-session confusion is a long-running, unattended Research sweep (backtest kernel/sweep/candidate work, often left running for hours) overlapping with a normal interactive session on anything else. So the only tag is `[Research]`, applied at `session close`/`session wrap` when that's what the session mostly did; everything else is untagged (no separate "Execution"/"Platform" label to maintain). Entries before 2026-08-08 predate this and are untagged too, same as any other non-Research entry. **`research`'s own scope is backtest/kernel work only** — prepping kernel/strategy changes and staging overnight sweep/backfill jobs, not general execution-reliability coding (that's `coder`/dispatched build work via `dispatch-to-peer`, or `[Monitor]` for something small enough to fix in the moment). Reaffirmed 2026-08-19 after a session drifted into general coding overnight with no separate lane to redirect to — `[Monitor]` (below) is that lane now.

**`[Monitor]` persona, added 2026-08-19**: a second tag, for a lightweight, low-context, all-day-open session distinct from planning (`planner`, night-time backlog sequencing) and building (`coder`, actual implementation, usually dispatched to background). Purpose: morning and periodic intraday check-ins confirming real order/position state matches expectation, available for quick intraday discussion, and filing backlog items as they come up — **never sequences or prioritizes the backlog**, only appends to it (`planner` picks up from there). Prefers running existing scripts (`daily-routine-check` skill, `watchlist_status.py`, `coverage_check.py`, etc.) over ad hoc DB/broker digging, specifically to keep context light across a day of check-ins; write a new script (per the "Standard, 2026-08-16" convention below) for any state-check likely to recur rather than repeating bespoke queries. May run as one session held open all day, or be freshly re-invoked — check in, document, done; not a discussion-first mode. `session_cache.md` entries from this persona get the `[Monitor]` tag, same mechanics as `[Research]` — `backlog_cache.md` entries stay on the existing domain-category tags only (`[live-trading]` etc.), same as every other session's backlog writes, since a backlog item has no single owning persona. New entries go right after `backlog_cache.md`'s header/preamble block (before the first `## [` line, matching how the file already reads newest-first) via a small anchor `Read` (offset 0, limit ~40) + `Edit` — never a full-file `Read`/`Write`, same cheap-insert pattern as `session_cache.md` prepends (see `feedback_cheap_log_inserts` memory).
- `go` — default: read the first ~60 lines of `docs/session_cache.md` (all entries, no filtering), the full `docs/backlog_cache.md`, and `docs/backlog_resolved_recent.md`, and summarize where things stand — the normal case when only one session is active. Also run `.venv/bin/python scripts/check_backlog_stale_dates.py` (cheap, mechanical) and surface any `(revisit ~date)` entries it flags as past due, instead of relying on catching it by eye during the read.
- `go research` — only when deliberately starting a **concurrent** session alongside an active/expected Research sweep, to scope the read to `[Research]`-tagged entries (plus untagged legacy ones) so it doesn't get confused reading notes from whatever else is happening in parallel. To keep this cheap, run `.venv/bin/python scripts/backlog_filter.py --tag backtest` (covers both `docs/backlog_cache.md` and `docs/backlog_resolved_recent.md` in one call) instead of reading either file directly — it extracts only entries carrying a `[backtest]` tag (anywhere in the tag list, e.g. `[backtest][live-trading]` counts) before the content reaches context, not just filtered by eye after a full read (found 2026-08-08: reading the full files and summarizing only the matching entries paid the same context cost as no filtering at all). This is a lossy filter (a research-relevant item could in principle be mistagged) — acceptable since the weekly cleanup pass re-triages/recategorizes backlog items anyway, so a miscategorized item won't stay invisible for long.
- `go monitor` — starting or resuming a `[Monitor]` check-in: run the `daily-routine-check` skill's state-verification sequence (real order/position state is the point, not backlog reading) and the first ~20 lines of `docs/session_cache.md` for same-day context. **Deliberately does not read `docs/backlog_cache.md` by default** — this persona only appends to the backlog, it doesn't consume or sequence it, and a full read would defeat the light-context goal for no benefit; look something up in it only if a specific check-in finding calls for it. Summarize state (orders/positions as expected? anything to flag?) and stop — check in, document, done, not a discussion-first mode.
- **Both `go` and `go research`**: since the full (or filtered) content is already being read into context either way, present deferred items (anything carrying a `(revisit ~YYYY-MM-DD)` tag, plus other clearly parked/low-priority entries) grouped separately in the summary from actionable-now items — don't mix them into one flat list. This is a presentation-time grouping only; **never restructure `docs/backlog_cache.md` itself to achieve this** (no physical reordering, no new section header written to the file) — the file's line-by-line convention (see its own header note) stays as-is, and it's frequently being edited concurrently by other sessions, so mutating it for a purely cosmetic read-time grouping is unnecessary risk for zero benefit (decided 2026-08-10, after almost doing exactly that).
- `session close` — session end: write the session summary entry (starting with `## <date> — <title>`, or `## <date> — [Research] <title>` if the session was mostly Research-sweep work, no surrounding `---`) to a file and run `python scripts/session_cache_update.py <file>` (or pipe via stdin) — this mechanically prepends to `docs/session_cache.md` (cap 10, drop oldest, gitignored) and appends to `docs/conversation_summary.md` (permanent, uncapped, committed) in one shot, no need to read either file first. Commit only `docs/conversation_summary.md`. No tests, no skills.
- `feature wrap` — mid-session feature complete: update relevant docs, review pre-commit checklist (`docs/pre_commit_checklist.md`) manually, and commit. Does not trigger session close. **Do not invoke any skills (especially verify) during this command.**
- `session wrap` — in order: (1) update relevant docs — if this session recorded a new policy/decision that touches a topic CLAUDE.md already has bullets about (ticker exclusions, account routing, a threshold, etc.), grep for older bullets on that same topic and reconcile them now, don't leave a contradiction for a future session to trip over (found 2026-08-19: a 2026-08-04 USO K-1 exclusion note went stale/self-contradicting after the 2026-08-12 K-1 policy generalization and nobody reconciled it — see `scripts/claude_md_staleness_check.py`, run periodically via the `weekend-cleanup` skill, for the mechanical half of this check), (2) review pre-commit checklist manually, (3) if `active_signals.py`, any `signals_*.py`/`schwab_*.py` module, or any backtest kernel module (`backtester.py`, `strategies.py`, `run_optimization_sweep.py`) changed this session: (3a) spawn TWO Opus review agents (`Agent` tool, `model: opus`) in parallel against the real diff of those changed files: one **independent/cold** (no session context, just the diff plus enough file-reading to judge it) and one **contextual** (given the session's actual intent/design decisions, so it can judge whether the implementation matches intent, not just internal consistency) — a single cold review is not sufficient, this pairing is required; once both return, do a rebuttal exchange (each agent's findings shown to the other, asked to confirm/refute) before summarizing to the user (severity + one-line description each, noting which findings survived rebuttal) and starting any fixes, then resolve any CONFIRMED findings before proceeding — a kernel bug is just as load-bearing as a live-trading bug, since paper trading/dry run/live all inherit whatever the kernel got wrong, (3b) if `active_signals.py`/`signals_*.py`/`schwab_*.py` changed, additionally run `python scripts/live_sim_harness.py` and confirm all scenarios pass, (3c) check `scripts/coverage_registry.py` (the Trade-Flow Accountability Grid) for any row whose `code_path`/`offline_coverage`/`notes` the session's changes made stale or wrong, and add a new row for any genuinely new logic branch (a new `scenario_key`/`log_coverage_event` call site) — flag a `scenario_key` collision with an existing row if the change reuses one; also check whether any truth table (`tests/test_entry_abandon_truth_table.py`, `tests/test_fake_broker_overlay_truth_table_scenario.py`, etc.) has a reachable-state/transition assumption the change invalidates, and whether canary/live-test setup (`docs/watchlist_candidate_checklist.md`, `docs/new_mechanism_promotion_standard.md`, `scripts/list_canary_nodes.py`'s A-F design) needs a new scenario for the change — state explicitly when none of this applies rather than skipping silently (found 2026-08-07: a real Grid update got left for the user to explicitly request, twice, after a live-incident fix), (4) write the session summary entry via `python scripts/session_cache_update.py` (see `session close` above) to update both `docs/session_cache.md` and `docs/conversation_summary.md`, (5) commit everything including both files. **Do not invoke any skills** (the Opus review agent above is a direct `Agent` tool call, not a skill).

## Research Log
`docs/research_log.md` (permanent, committed, append-only) is a lab notebook of real experiments run against this system — hypothesis, method, result, verdict, follow-up — distinct from `docs/backlog_cache.md` (current, actively-trimmed pointer list of **open items only**, read in full every session start), `docs/backlog_resolved_recent.md` (rolling ~7-day window of recently-resolved one-liners, for session-handoff context — also read in full every session start, but pruned of anything older since `deep_backlog.md` already has it permanently), `docs/deep_backlog.md` (permanent full-detail archive of every backlog item, resolved or not — resolved items are kept in place and marked ✅, never deleted), and `docs/conversation_summary.md` (session narrative). Append an entry to the research log directly (no capping/pruning logic, no wrapper script needed — a plain append) whenever a real experiment produces a finding, whether or not it also produces code changes or a backlog item — don't wait for session close. When a backlog item is resolved: (1) add or update its full-detail entry in `docs/deep_backlog.md` (marked ✅, matching that file's existing style) so it's never lost, (2) if the resolution is mostly research narrative (hypothesis/method/result) rather than an action record, also write a `docs/research_log.md` entry and have the `deep_backlog.md` entry point to it instead of duplicating the writeup, (3) prepend a one-line pointer to `docs/backlog_resolved_recent.md` (dropping any entries there older than ~7 days), and (4) remove the item from `docs/backlog_cache.md` entirely (not just shrink it — resolved items don't stay in the open-items file at all now).

## Project Overview
A z-score mean reversion backtesting and optimization system targeting leveraged ETFs. Runs parallel grid sweeps over take profit, stop loss, and hold time parameters to find optimal strategy configurations with positive alpha vs SPY. Now in live trading phase with manual execution via Schwab.

**Schema-migration smoke-test convention (2026-08-15)**: to confirm a new `ensure_tables()` migration applies cleanly against real production shape/data (not synthetic test data), copy the latest snapshot from `output/live_backups/` to a scratch/temp location first, then run `ensure_tables()`/`run_all()` against that copy — never against the live `cache/live/trading_live.db` directly, and never in-place against the backup file itself (the backup is the real disaster-recovery point and must stay pristine and untouched).

## Architecture Notes
- Optimization uses `ProcessPoolExecutor` with up to 10 workers
- Results cached in SQLite to avoid re-running completed nodes
- Multi-generation refinement: macro grid scan → frontier detection → fine mesh around top performers
- `active_phase_grid.json` is written by the sweep and read by the Streamlit UI for live progress display
