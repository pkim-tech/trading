# Backlog Cache

> **Open items only.** Resolved items live permanently in `docs/deep_backlog.md`; a rolling
> window of recently-resolved one-liners (for session-handoff context) lives in
> `docs/backlog_resolved_recent.md`, pruned to entries from roughly the last week — anything
> older is fully covered by `deep_backlog.md` and doesn't need re-reading here. `go` reads this
> file plus `backlog_resolved_recent.md` in full each session; keep both lean.
>
> **Maintenance**: when an item here resolves — (1) add/update the full-detail entry in
> `deep_backlog.md` (unchanged convention), (2) prepend a one-liner to
> `backlog_resolved_recent.md`, (3) drop entries from `backlog_resolved_recent.md` older than
> ~7 days (already permanent in `deep_backlog.md`), (4) remove the item from this file. When a
> genuinely new backlog item is raised, add a 1-2 line entry here directly (no full-detail
> writeup needed unless/until it resolves). **"Downgraded"/"deprioritized" is not a resting
> state** (found 2026-08-16, after two items sat as "downgraded" for a full session, resurfacing
> on every `go` read despite being fully decided) — once a real decision is reached (accept the
> residual risk, skip, defer with an explicit revisit trigger), close the item out via the same
> 4 steps above like any other resolution, don't leave it lingering here just because the
> decision was "don't fix" rather than "fixed."
>
> **Prioritization**: `docs/roadmap.md` holds the phased "where are we headed and in what
> order" vision (universe sweep for overlay-friendly nodes → portfolio construction → modest
> live capital → trend/edge-decay detection → scale up). Triage open items below against it —
> an item serving the current phase generally outranks one serving a later phase.
>
> **Deferral**: an item that's real but genuinely not worth touching yet gets a
> `(revisit ~YYYY-MM-DD)` tag appended to its header line, instead of just sitting in the list
> looking equally actionable as everything else. `go` should flag (not auto-resolve or drop)
> any deferred item whose date has already passed, so it surfaces again instead of quietly
> aging out. No separate section — stays in place, in normal open-items order.
>
> **Condition-based deferral** (2026-08-15): some items don't wait on a date, they wait on a
> real-world condition (e.g. "the user has a WFH day free to safely test against a real
> broker") that no fixed date can predict. For these, tag the header `(revisit when: <condition>)`
> instead of a date — `go` cannot mechanically check a condition-based trigger the way it checks
> a past date, so a future session reading the item should ask the user directly whether the
> condition now holds, rather than assuming a stale-looking item is dead.
>
> **Specced tag** (2026-08-20): once an item's design/approach is actually decided (not just
> discussed) but the build itself hasn't started, add `[specced]` to its tag list — lets a
> session filter to non-specced items (the ones still needing a design decision, not just an
> implementer) when that's the actual bottleneck. Add a one-line note of what was decided right
> in the header/body when tagging it, so the spec isn't just the tag alone. Remove the tag (or
> just close the item) once it's built.
